Deadlock Analysis and Resource Allocation Dashboard

Four necessary (Coffman) conditions

Deadlock needs all four at once: mutual exclusion, hold and wait, no preemption, circular wait. Breaking any one prevents deadlock.

Prevention

Design the policy so one condition can never hold (e.g. global resource ordering removes circular wait; request-all-at-once removes hold and wait). Cost: lower utilisation or concurrency.

Avoidance (Banker’s Algorithm)

Needs each process’s maximum claim in advance. Grants a request only if the resulting state is safe. It does not detect an existing deadlock.

Detection

Lets deadlock happen, then finds it: wait-for graph cycle (single-instance) or the matrix detection algorithm (multiple-instance).

Recovery

After detection: terminate a process (or preempt resources). Its resources are released so the others can progress.

State labels used in this dashboard (never interchangeable)

SAFEA complete safe sequence exists.
UNSAFENo complete safe sequence exists. Deadlock may follow, but processes may not have requested their maximum yet, so it is not necessarily deadlock.
WAITING / DEFERREDA valid request (≤ Need) exceeds Available. Not invalid, not permanently denied; the process waits.
DEADLOCKEDAn existing set of processes each waiting for resources only others in the set can release (found by detection).
INVALID INPUTBad process ID, negative or non-integer value, wrong vector length, Allocation > Maximum, or request > remaining Need.
